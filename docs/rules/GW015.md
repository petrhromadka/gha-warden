# GW015: Entire secrets context exposed

**Severity:** high

## What it detects

An expression anywhere in the workflow (`env:`, `with:`, `run:`, a
`github-script` `script:`, and so on) that hands over more than one named
secret:

- `${{ toJSON(secrets) }}`, `${{ secrets }}` or any other use of the bare
  `secrets` context.
- `secrets[...]` with an index that is not a string literal, for example
  `${{ secrets[matrix.name] }}` or `${{ secrets[format('{0}_TOKEN', inputs.env)] }}`.
  `secrets['NAME']` with a literal name is the same as `secrets.NAME` and is not
  reported.

It also reports `toJSON(github)` and `toJSON(github.event)` inside a `run:`
script, because they paste the whole event payload into the shell.

## Why it's dangerous

Every secret the repository can read is in the `secrets` context. Passing all
of it to one step defeats least privilege: that step, and every action or
script it runs, can read secrets it has no use for, and a compromise of one
action leaks all of them. A dynamic index has the same effect in a smaller way,
because a reviewer cannot tell from the file which secrets the step can reach.

GitHub also advises against bundling secrets into structured data such as JSON,
because log redaction relies on matching the exact secret value and fails once
the secret is encoded inside a blob. `toJSON(secrets)` is exactly that blob.

`toJSON(github.event)` is a different problem. The event payload contains
issue and pull request titles and bodies, branch names, commit messages and
author names, all chosen by whoever opens the issue or PR. `toJSON` escapes the
double quote but not the single quote, so `echo '${{ toJSON(github.event) }}'`
lets a title containing `'` end the quoted string and run commands, the same
attack as [GW001](GW001.md). GW001 only matches a fixed list of known fields, so
a whole-object dump needs its own check. Inside `env:`, the same expression is
safe, because the shell reads the value from the environment instead of parsing
it.

## Vulnerable example

```yaml
name: notify
on:
  issues:
    types: [opened]

permissions:
  contents: read

jobs:
  notify:
    runs-on: ubuntu-latest
    steps:
      - uses: example-org/notify-action@8aa5831fb8d48d8f76594c7ddde61ae58019f550 # v1.0.0
        with:
          credentials: ${{ toJSON(secrets) }}
          webhook: ${{ secrets[format('{0}_WEBHOOK', github.event.issue.user.login)] }}
      - run: |
          echo "event: ${{ toJSON(github.event) }}"
```

## Fixed example

```yaml
name: notify
on:
  issues:
    types: [opened]

permissions:
  contents: read

jobs:
  notify:
    runs-on: ubuntu-latest
    steps:
      - uses: example-org/notify-action@8aa5831fb8d48d8f76594c7ddde61ae58019f550 # v1.0.0
        with:
          webhook: ${{ secrets.CHAT_WEBHOOK }}
      - run: echo "$ACTION"
        env:
          ACTION: ${{ github.event.action }}
```

Name each secret the step needs. If the choice of secret depends on the
environment, use a job-level `environment:` so the same secret name resolves to
a different value, or write an explicit `if:` for each variant. To read event
data in a script, pass the fields you need through `env:`, or read them with
`jq` from the file at `$GITHUB_EVENT_PATH` instead of pasting the payload into
the script.

## Suppressing

Put the comment on the line the finding points at:

```yaml
          credentials: ${{ toJSON(secrets) }}  # gha-warden: ignore[GW015]
```

Suppress it only for a trusted, pinned action that is documented to need the
whole context.
