# GW006: Reusable workflow called with `secrets: inherit`

**Severity:** medium

## What it detects

A job that calls a reusable workflow (`uses: owner/repo/.github/workflows/x.yml@ref`
or `uses: ./.github/workflows/x.yml`) and sets `secrets: inherit`.

## Why it's dangerous

`secrets: inherit` hands the called workflow every secret that the caller can
access: repository, environment and organization secrets alike. The caller no
longer lists which secrets the callee needs, so a review of the call site does
not show what is exposed. If the called workflow lives in another repository,
or is referenced by a mutable ref such as `@main`, whoever can change it can
read all of those secrets with one commit. A later edit to the called workflow
that starts using an extra secret gets access to it silently. Passing secrets
by name keeps the exposure visible and limited to what the callee declared.

## Vulnerable example

```yaml
name: deploy
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  deploy:
    uses: example-org/shared-workflows/.github/workflows/deploy.yml@main
    secrets: inherit
```

## Fixed example

Pin the called workflow to a commit SHA and pass only the secret it needs.

```yaml
name: deploy
on:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  deploy:
    uses: example-org/shared-workflows/.github/workflows/deploy.yml@0123456789abcdef0123456789abcdef01234567
    secrets:
      DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}
```

The SHA above is a placeholder: use the commit of your own shared workflow.

## Suppressing

Put the comment on the line the finding points at:

```yaml
    secrets: inherit  # gha-warden: ignore[GW006]
```

Suppress it when the called workflow is in the same repository and you review
every change to it as you review the caller.
