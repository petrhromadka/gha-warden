# GW004: Excessive `GITHUB_TOKEN` permissions

**Severity:** medium

## What it detects

Either of these:

- `permissions: write-all` at the workflow or job level.
- A workflow with no top-level `permissions:` block that contains a job
  without its own `permissions:` block.

## Why it's dangerous

Every job receives a `GITHUB_TOKEN`. When a workflow does not restrict it, the
token gets the default permissions of the repository or organization, which
can include write access to contents, packages, pull requests and more.
`write-all` grants every scope explicitly. If any step in the job is
compromised, through a script injection or a malicious third-party action, the
attacker inherits that token. With `contents: write` they can push a commit or
move a tag, and with `packages: write` they can publish an artifact under
your name. Granting only the scopes a job needs limits the damage of such a
compromise.

## Vulnerable example

```yaml
name: ci
on: [push]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: make test
```

The same finding appears for an explicit grant of everything:

```yaml
name: ci
on: [push]

permissions: write-all

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: make test
```

## Fixed example

Set a read-only default at the top of the workflow and raise it per job only
where needed.

```yaml
name: ci
on: [push]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: make test

  comment:
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
    steps:
      - run: echo "this job may comment on pull requests"
```

## Suppressing

Put the comment on the line the finding points at:

```yaml
permissions: write-all  # gha-warden: ignore[GW004]
```
