# GW011: Cache poisoning in privileged workflow

**Severity:** medium

## What it detects

A workflow triggered by `pull_request_target`, `workflow_run` or
`issue_comment` that restores a cache. The finding points at the `uses:` line
of the step:

- `actions/cache` or `actions/cache/restore`
- `actions/setup-node`, `actions/setup-python` or `actions/setup-java` with a
  `cache:` input that is set (anything other than empty or `false`)
- `actions/setup-go`, which caches by default, unless `cache: false`
- `astral-sh/setup-uv` with `enable-cache: true`

`actions/cache/save` alone is not reported, because it does not restore
anything. Setup actions that enable caching on their own (for example
`astral-sh/setup-uv` without `enable-cache`) are not reported either.

Release workflows (`release` or tag pushes) that restore caches are not
reported. Nearly every release workflow uses a dependency cache, and whether
an attacker can reach that cache depends on other workflows in the repository,
which a per-file scan cannot see.

## Why it's dangerous

Caches are shared between workflows of a repository. A workflow that runs
attacker-controlled code, such as a `pull_request_target` job that builds the
pull request, can write any cache entry under any key, even with
`permissions: {}`, because the cache service does not use the `GITHUB_TOKEN`.
Entries written in the context of the default branch are readable by every
other branch. The attacker fills the cache with a poisoned `node_modules`,
virtual environment or build directory, and a later privileged workflow
restores it and runs it with a write token or secrets. The researcher who
described this technique used it to reach production deployment secrets of
several well-known projects. The three triggers above run in the context of the
base or default branch, so the entries they write are visible to other
workflows, and the entries they restore may have been written by an attacker.

## Vulnerable example

```yaml
name: label-pr
on:
  pull_request_target:
    types: [opened]

permissions:
  contents: read
  pull-requests: write

jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-node@v4
        with:
          cache: npm
      - run: npm ci && node scripts/label.js
```

## Fixed example

Do not restore a cache in a workflow that holds a write token or secrets. The
install is a little slower, but nothing an attacker wrote is executed.

```yaml
name: label-pr
on:
  pull_request_target:
    types: [opened]

permissions:
  contents: read
  pull-requests: write

jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7.1.0
        with:
          cache: ""
      - run: npm ci --ignore-scripts && node scripts/label.js
```

Better still, run pull request code only in unprivileged `pull_request`
workflows, and keep the privileged workflow free of builds and caches.

## Cross-workflow analysis

When several workflow files are scanned together (for example `gha-warden .github/workflows`),
a `workflow_run` trigger is not reported if every workflow named in `workflow_run.workflows`
is among the scanned files and none of them, directly or through further `workflow_run`
chains, can be started by untrusted input (`pull_request`, `pull_request_target`,
`issue_comment`, `pull_request_review`, `pull_request_review_comment`, `issues`, `discussion`,
`discussion_comment`, `fork` or `watch`), because a fork can then never reach this workflow.
If an upstream workflow is missing from the scan, or the name is a pattern, the finding is
kept. Other privileged triggers in the same file are unaffected.

## Suppressing

Put the comment on the `uses:` line the finding points at:

```yaml
      - uses: actions/cache@v4  # gha-warden: ignore[GW011]
```

Suppress only when no workflow that runs untrusted code can write the same
cache key, for example because the cache key includes a value that only this
workflow produces.
