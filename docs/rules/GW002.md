# GW002: Pwn request (untrusted checkout in a privileged workflow)

**Severity:** critical

## What it detects

A workflow triggered by `pull_request_target`, `workflow_run` or
`issue_comment` that checks out or fetches code from a pull request. These are
the privileged triggers: they run in the context of the base repository with a
write token and access to secrets. The rule reports four patterns.

1. `actions/checkout` with a `ref:` (or `repository:`) pointing at code from the
   pull request:
   - `github.event.pull_request.head.sha`, `.head.ref`, or other
     `github.event.pull_request.head.*` values
   - `github.head_ref`
   - `github.event.workflow_run.head_sha`, `.head_branch`, or other
     `github.event.workflow_run.head_*` values
   - any `refs/pull/...` ref, such as
     `refs/pull/${{ github.event.issue.number }}/head`, which is how an
     `issue_comment` workflow usually names the pull request
2. `actions/checkout` whose `ref:` or `repository:` is an output of an earlier
   step in the same job (`${{ steps.pr.outputs.head_sha }}`) when that step
   resolves the pull request head: it uses
   `xt0rted/pull-request-comment-branch`, or its `run:` or `github-script`
   code calls `pulls.get`, `gh pr view`, `gh api .../pulls/...`, or reads
   `head.sha`, `head.ref`, `head_sha` or `headRefOid`.
3. A `run:` step that runs `gh pr checkout`.
4. A `run:` step that fetches a pull request ref
   (`git fetch origin pull/123/head`), or runs `git checkout`, `switch`,
   `reset`, `merge`, `cherry-pick`, `clone`, `fetch` or `pull` with one of the
   untrusted values from item 1, for example
   `git checkout ${{ github.event.pull_request.head.sha }}`.

## Why it's dangerous

`pull_request_target`, `workflow_run` and `issue_comment` run in the context of
the base repository. They get a `GITHUB_TOKEN` that can write and they can read
the repository's secrets, even when the pull request comes from a fork. If such
a workflow then checks out the pull request's head and runs anything from that
tree, the attacker's code runs with those privileges. "Anything" includes
`npm install` (lifecycle scripts), `make`, a test runner, or a local action
that the pull request modified. An attacker opens a pull request from a fork
that changes `package.json` to run a script, and the script sends the
repository secrets to a server they control. GitHub Security Lab calls this
pattern a "pwn request".

`issue_comment` is easy to miss because it does not mention the pull request in
its payload. A "/test" or "/deploy" comment command has to look up the pull
request first, then check out its head. The comment event always runs the
workflow file from the default branch, so the workflow is privileged, while the
code it fetches is whatever the fork's author pushed. Anyone who can comment can
start the run.

## Vulnerable example

```yaml
name: pr-build
on:
  pull_request_target:
    types: [opened, synchronize]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          ref: ${{ github.event.pull_request.head.sha }}
          persist-credentials: false
      - run: npm ci && npm test
```

An `issue_comment` variant. The checkout `ref:` is reported because it is
an output of a step that resolves the pull request head:

```yaml
name: pr-command
on:
  issue_comment:
    types: [created]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    if: github.event.issue.pull_request && startsWith(github.event.comment.body, '/test')
    steps:
      - id: pr
        uses: xt0rted/pull-request-comment-branch@<full-commit-sha> # v3
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          ref: ${{ steps.pr.outputs.head_sha }}
          persist-credentials: false
      - run: make test
```

The same rule reports `run: gh pr checkout ${{ github.event.issue.number }}`,
`git fetch origin pull/${{ github.event.issue.number }}/head`, and
`git checkout ${{ github.event.pull_request.head.sha }}` in these workflows.

## Fixed example

Use the unprivileged `pull_request` trigger for anything that builds or tests
pull request code. It runs without secrets for fork pull requests.

```yaml
name: pr-build
on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: npm ci && npm test
```

If a privileged follow-up step is needed (for example commenting on the pull
request), split the work in two. The untrusted build runs under `pull_request`
and uploads its result as an artifact. A separate `workflow_run` workflow
downloads the artifact, treats it as untrusted data, and never checks out or
executes pull request code.

For an `issue_comment` command such as `/test`, do not check out the pull
request in the comment workflow. Let the comment workflow only record the
request (for example by adding a label, after checking the commenter's
permission), and run the build in a `pull_request` workflow that reacts to
the `labeled` event. That workflow runs without secrets for fork pull requests.

## Suppressing

Put the comment on the line the finding points at:

```yaml
          ref: ${{ github.event.pull_request.head.sha }}  # gha-warden: ignore[GW002]
```

Suppress only when the checked-out code is never executed or built, and only
files are read as data, for example a label-gated job that only counts lines.
