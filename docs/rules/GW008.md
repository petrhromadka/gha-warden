# GW008: `ACTIONS_ALLOW_UNSECURE_COMMANDS` enabled

**Severity:** high

## What it detects

The environment variable `ACTIONS_ALLOW_UNSECURE_COMMANDS` set in `env:` at
the workflow, job or step level. The rule reports any enabling value, such as
`true`.

## Why it's dangerous

GitHub disabled the `::set-env` and `::add-path` workflow commands in
October 2020 after a vulnerability in the Actions runner (CVE-2020-15228).
Any step that writes text to standard output can emit these commands. If that
text includes untrusted data, such as an issue title or a file name from a
pull request, the attacker can inject a line like
`::set-env name=LD_PRELOAD::/tmp/evil.so` or `::add-path::/tmp/bin`. Later
steps in the job then run with an environment variable or a `PATH` directory
that the attacker chose, which leads to code execution in the job.
`ACTIONS_ALLOW_UNSECURE_COMMANDS: true` switches the commands back on.

## Vulnerable example

```yaml
name: legacy
on: [push]

permissions:
  contents: read

env:
  ACTIONS_ALLOW_UNSECURE_COMMANDS: "true"

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "::set-env name=MODE::release"
```

## Fixed example

Write to the environment files `$GITHUB_ENV` and `$GITHUB_PATH` and remove
the variable.

```yaml
name: legacy
on: [push]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "MODE=release" >> "$GITHUB_ENV"
```

If an old action in your workflow still needs the unsafe commands, update or
replace the action instead of enabling the flag.

## Suppressing

Put the comment on the line the finding points at:

```yaml
  ACTIONS_ALLOW_UNSECURE_COMMANDS: "true"  # gha-warden: ignore[GW008]
```
