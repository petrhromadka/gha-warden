# GW012: Artifact poisoning

**Severity:** high

## What it detects

A workflow triggered by `workflow_run` or `pull_request_target` that downloads
artifacts produced by another run, and then, later in the same step or in a
later step of the same job:

- writes the content of a downloaded file to `$GITHUB_ENV`, `$GITHUB_OUTPUT`,
  `$GITHUB_PATH` or `$GITHUB_STATE` (`cat out/env.txt >> "$GITHUB_ENV"`,
  `echo "pr=$(cat out/pr-number)" >> "$GITHUB_OUTPUT"`, or a
  `while read` loop that reads the file and writes each line)
- runs or sources a downloaded file (`source out/env.sh`,
  `bash artifacts/deploy.sh`, `. ./artifacts/env`, `./artifacts/tool`)
- runs a build tool on downloaded content (`npm ci`, `make`, `pip install`,
  `cargo build` and similar, after `cd`, with `working-directory:`, or with
  the directory as an argument)
- in `actions/github-script`, reads a downloaded file (`fs.readFileSync`) and
  calls `core.exportVariable`, `core.setOutput` or `core.addPath`, or loads a
  downloaded file with `require()`

A download is one of:

- `actions/download-artifact` with a `run-id` or `github-token` input (without
  them it only reads artifacts of the current run)
- `dawidd6/action-download-artifact`
- `gh run download` in a `run:` script

The finding points at the download step, and the message names the step that
uses the artifact.

### Which files count as downloaded

The rule follows the download destination through each script:

- The destination is `path:` of the download action or `--dir` / `-D` of
  `gh run download`. `${{ runner.temp }}` and `$RUNNER_TEMP` are the same
  directory, and `${{ github.workspace }}/x`, `$GITHUB_WORKSPACE/x` and `x` are
  the same path.
- Without a destination (or with `.` or an expression it cannot resolve) the
  artifact lands in the workspace, so any file the job reads, runs or builds
  in the workspace may be the artifact: every file read counts, and running a
  checked-out script such as `./scripts/x.sh` or `npm ci` counts too, because
  the artifact can overwrite it.
- With a known destination, only paths inside it count. A path can also reach
  a command through a variable: `F=out/env.txt` (also with `export`, `local`,
  `readonly`), `for f in out/*`, or an `env:` entry of the workflow, job or
  step, including `${{ steps.<id>.outputs.download-path }}` of the download
  step. A file the job writes itself, outside the destination, is not counted.

Writes that are reduced to digits (`tr -cd '0-9'`, `| tonumber`, or
`grep -E '^[0-9]+$'`) are not reported; in a loop, the loop body counts. In
`actions/github-script`, a script that converts with `Number()`, `parseInt()`
or `parseFloat()`, or tests `/^\d+$/`, is not reported. Reading the webhook
payload (`$GITHUB_EVENT_PATH`) is not counted as reading an artifact.

### Limits

The analysis is per line and per step, not a shell parser. It prefers missing
an unusual case to reporting a guess:

- File *content* held in a variable is not followed:
  `PR=$(cat out/pr); echo "pr=$PR" >> "$GITHUB_OUTPUT"` is not reported. Such
  scripts usually validate the variable first (`[[ $PR =~ ^[0-9]+$ ]]`), and
  telling validated from unvalidated variables needs more than a line-based
  check.
- Variables are followed only when they are set to one word without command
  substitution, before use, in the same script; values set in an earlier step
  through `$GITHUB_ENV` or step outputs are not followed (except
  `download-path` of the download step).
- `while read` loops are matched from the `while` line to the next `done`;
  nested loops are not tracked separately.
- In `actions/github-script`, a script that reads a file and calls
  `core.setOutput` is reported when any string in it names a path in the
  download directory; paths built from `process.env` are not resolved.
  Artifacts downloaded by `actions/github-script` itself (with
  `downloadArtifact` and `unzip`) are not recognized as downloads.
- Only the steps after the download in the same job are checked; a job that
  receives the content through `needs` outputs is not.

## Why it's dangerous

`workflow_run` and `pull_request_target` workflows run with a write token and
secrets. The artifacts they download often come from a `pull_request` run that
executed the attacker's code, so the attacker decides every byte. A value
written to `$GITHUB_ENV` can set `LD_PRELOAD`, `NODE_OPTIONS` or `BASH_ENV` and
turn into code execution in the next step. A line break in an output injects
extra outputs. A downloaded script or build file simply runs with the
privileges of the privileged workflow. An attacker can also change the
triggering workflow in their pull request, so the "trusted" workflow that
uploads the artifact gives no guarantee.

## Vulnerable example

```yaml
name: pr-comment
on:
  workflow_run:
    workflows: [CI]
    types: [completed]

permissions:
  pull-requests: write

jobs:
  comment:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}
          path: pr
      - run: cat pr/env.txt >> "$GITHUB_ENV"
```

## Fixed example

Treat the artifact as data. Unpack it outside the workspace, validate the one
value you need, and never execute or build anything from it.

```yaml
name: pr-comment
on:
  workflow_run:
    workflows: [CI]
    types: [completed]

permissions:
  pull-requests: write

jobs:
  comment:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@9000827ccba6bdab643e8b6fd33ac0654aef8333 # v8.0.2
        with:
          run-id: ${{ github.event.workflow_run.id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}
          path: ${{ runner.temp }}/pr
      - id: pr
        run: echo "number=$(tr -cd '0-9' < "$RUNNER_TEMP/pr/number")" >> "$GITHUB_OUTPUT"
```

## Cross-workflow analysis

When several workflow files are scanned together (for example `gha-warden .github/workflows`),
a `workflow_run` trigger is not reported if every workflow named in `workflow_run.workflows`
is among the scanned files and none of them, directly or through further `workflow_run`
chains, can be started by untrusted input (`pull_request`, `pull_request_target`,
`issue_comment`, `pull_request_review`, `pull_request_review_comment`, `issues`, `discussion`,
`discussion_comment`, `fork` or `watch`), because a fork can then never reach this workflow.
If an upstream workflow is missing from the scan, or the name is a pattern, the finding is
kept. Other privileged triggers in the same file are unaffected.

## Suppressing

Put the comment on the download step's `uses:` line (or on the `gh run
download` line in a `run:` script):

```yaml
      - uses: actions/download-artifact@v4  # gha-warden: ignore[GW012]
```

Suppress only when the artifact is produced by a trusted workflow that never
runs pull request code, and say so in a comment next to the suppression.
